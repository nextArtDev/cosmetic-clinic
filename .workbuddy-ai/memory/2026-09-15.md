# 2026-09-15 — /v16: clipping + early-reveal bug sweep

Follow-up on the user's report ("some texts are cutted out … some parts appear
too soon to see them"). Two of the four items were already fixed (double mobile
dock, hero media gap); this pass took the other two.

## Root cause behind "appears too soon"

`MediaGrid` (Showcase.tsx) grew **354px → 640px** after its images loaded: tile 0
spans both grid rows and its media div had `lg:aspect-auto` + an in-flow `<img>`,
so the image's intrinsic height sized the two `auto` rows. That added **+286px of
document height** (20131 → 20417), which invalidated every `ScrollTrigger`
position computed at load — so sections below the MediaGrid revealed ~286px
early, i.e. while still under the fold. Measured with `probe-faq.mjs`: each FAQ
row reached opacity 1 with **0px visible**; after the fix, **fully visible**.

Fixes:
- `Showcase.tsx` — tile 0's media is now `lg:absolute lg:inset-0 lg:aspect-auto`
  and every tile's `<img>` is `absolute inset-0`, so no image contributes height.
- `MayaApp.tsx` — `ScrollTrigger.config({ autoRefreshEvents: "DOMContentLoaded,load,resize" })`
  (the theme's own setting) + a debounced `ResizeObserver` on `document.body` +
  a `load` listener. Document is now a constant 20131px first paint → bottom.
- `bits.tsx` — `Reveal` with `stagger` now uses `ScrollTrigger.batch` over its
  `[data-rv]` children instead of one trigger on the wrapper's top edge. A tall
  wrapper (the FAQ list is ~530px) fired at 84% of its *top*, so the last rows
  animated off-screen.
- `StackedCollection.tsx` — batch start `top 94%` → the engine's `top 80%`.

## Root cause behind "texts are cutted out"

- **`richText` / Statement**: the engine's `gsap.set([rich-animated-color], { scale: 20 })`
  targets `.animate-round` — a decorative disc in `.animate-round-wrap`
  (absolute, inset 0, overflow hidden) positioned to sit behind the centre
  badge. The port had applied `scale: 20` to the SALE badge itself, so the
  section opened as a full-viewport clay field hiding the manifesto. Rebuilt
  the section: added `.maya-round-wrap` / `.maya-round`, and rebuilt the row as
  the real `.collection-items-7` — seven *circular* cells (70/100/140/180/140/100/70
  at ≥1200px) overlapping via negative margins, pinned to the panel bottom.
- **Footer watermark**: `text-[24vw] leading-[0.8]` + `-mb-[4vw]` meant the line
  box was smaller than Vazirmatn's ~1.37em ascent+descent, so the footer's
  `overflow-hidden` sheared the bottom off "مایا". Also the parallax was driven
  off the wordmark's own box, whose bottom *is* the document bottom — so
  `end: "bottom bottom"` landed on the last scrollable pixel and the scrub only
  reached ~24% (transform stuck at +124px). Now: `leading-[1.45]`, trailing
  `pb`, and the trigger is the `<footer>` itself. Scans to `ty=0` with **0px**
  footer overflow.

## Environment notes

- `window.lenis` is a **stub** (only a `version` key) — not the Lenis instance.
  Plain `window.scrollTo(0, y)` does land and stick, so it is the reliable way
  to park the page in probes. Do NOT use `window.lenis.scrollTo`.
- `probe-audit`'s resting check must parse **both** `matrix(...)` and
  `matrix3d(...)`; gsap emits `matrix3d` whenever `preserve-3d` is set, and a
  regex that only matches `matrix(` silently treats a `scale: 20` deck as at rest.
- The BestSellers "broken layout" in a sweep frame was a probe artefact: the
  cursor-follow preview keeps its last position because the probe only moves the
  mouse once, and `hovered !== null` dims the other rows.

### Audit false positive to remember

The footer wordmark shows `anc=x0 y117` in `probe-audit`. That is **not** a
clip: the audit measures at scroll 0, where the wordmark's *parallax* is still
at its start offset (~+203px), so its rect escapes the footer's box — but the
footer is off-screen at that point. `probe-mark2.mjs` (new) parks at the bottom,
lets the scrub settle, and measures the **glyph** rects (`Range.getClientRects`)
against the clipping ancestor: at rest the wordmark sits fully inside the footer
(`dy=0`), and `footer-mark.png` confirms the outlined "مایا" is intact.
Rule of thumb: judge an audit hit by whether it is clipped *when on-screen*.
Added this caveat to the probe header.

## User bug report: colours + the "STYLE CRAFTED TO PERFECTION" section

Two issues, both root-caused against the reference rather than guessed at.
The screenshots the user pasted were **not** materialised on disk
(`find /c/Users/aria -iname "Clipboard_Screenshot*"` → nothing), so both were
diagnosed by rendering the port and the reference mirror myself.

### 1. The whole palette was wrong (committed in `f5370fc`)

The port shipped a **warm cream/brown** theme (`--color-maya-cream: #f2ede4`,
`--color-maya-clay: #9a6a3d`). The reference's `:root, .scheme-primary` block
is a **monochrome** system:

```
body-background #ffffff   text/heading-color #000000
card-background #f4f4f4   border-color #dddddd
body-alternate-background #f1f1f1   image-bg #a9a3a3
link-hover-color #5e5e5e  button #000 on #fff (and inverted)
```

Measured tally of the reference's 19 sections: 12 white (6 of them with a
background image), 4 dark (`#212123` / `#242427`), 2 `#f1f1f1`, 1 transparent.
Token **names** were kept so all 24 components kept working; only the values
changed, plus a new `--color-maya-card` for the reference's `card-background`.
`probe-colors.mjs` samples every section's computed bg/text in both DOMs.

### 2. `featured_collections_tabs` was structurally wrong (committed in `fb14bbe`)

`FeaturedTabs.tsx` rendered three full-width list rows with the display
heading trapped in a white pill → a long Persian heading wrapped and spilled
out of its own background ("crashed texts"), and there was no mosaic at all.

The reference (`methodCalled="featuredCollectionsList"`) is **four stacked
layers** in one pinned stage, and the port now matches:

| layer | reference | measured |
|---|---|---|
| front | `.featured-collections-list-front` abs-centred, `fade-out-text` on pin | — |
| chips | `.featured-collections-list-tabs` centred deck | 106×86 / **475×86 active** desktop, 80×60 / **280×60** mobile |
| text | `.featured-collections-list-text` ×3 stacked in one grid cell | h2 + 2 paragraphs |
| media | `.featured-collections-list-tabscontent-inner` | hero + 2 squares + caption pill + wide tile |

**The "4 images" are per collection**: 1 `list-mainmedia` (absolutely filling)
+ 2 squares (`--image-ratio:100%`) + 1 full-width (`ratio:60%`) — 9
`multi-media-img` across 3 collections. The engine's `onUpdate` shrinks every
main media to `scale 0` and scales the tiles to `1`, so the hero *resolves
into* the mosaic. That is the "multi-step animation" the user described.

Timeline phases (kept): hero in from `xPercent -100 / scale .7`; the
description rail `width 0 → 100%`; the rule `scaleX 0 → 1 → 0`. Verified
transforms: hero `matrix(0.7,…,−536,0) → matrix(1,0,0,1,0,0)`; tiles
`243×243` + `506×304`; docH constant **20208**; audit 73 desktop / 128 mobile,
8/8 reveals, 0 console errors; `overflowX false`.

Each collection swaps the section's colour scheme (the engine does
`section.classList.replace(oldScheme, newScheme)`): crimson / olive / orange
radials, transcribed into a `SCHEMES` array in the component.

### Gotchas worth keeping

- **A wrapping label inside a background-painted pill silently "crashes"**:
  `.maya-ft-pill::before { inset: 0 }` paints exactly the element box, so if
  the text wraps to a second line the trailing glyphs land outside the
  background. The reference's chip label is `white-space: nowrap`, which is
  why it never happens there.
- `probe-tabs-compare.mjs` must `scrollIntoView` the section *before*
  sampling: the reference pins with gsap, so a pre-pin absolute offset lands
  on a completely different section (it shot the bundle section first).
- The reference's `.featured-collections-list-tabs` is `position: fixed` at
  `calc(50% - var(--list-tabs-height)/2.4)` and moves to `top: 0` once pinned;
  the port expresses the same thing with `position: absolute` inside the
  sticky panel.




## Closed the flagged item: the mobile tabs panel clipped 265px

I had flagged, unverified, that the mobile typewriter line / rule might be cut
by the `100svh` panel. Measured it properly
(`scripts/maya/probe-ft-mobile-clip.mjs` — walks every child of the panel and
diffs its rect against the panel box across the whole pin, on port and
reference):

- the **text** column was fine (textcol 96..524 inside [0..844]); my worry was
  misplaced.
- the **media** column was not: `mediacol` 320..1109 → **265px clipped**. The
  wide tile (`tile[8]` / `wide[2]`) sat at 896..1094, i.e. **entirely
  off-panel and never visible**, and the caption pill was cut 32px. That is
  literally the user's "in mobile, even doesnt show the original image
  correctly".

Root cause is in the theme's own CSS, not in the port's transcription of the
engine: `featured-collections-tabs.css` scopes BOTH the chip deck's
`position: fixed` and the head's / hero's `position: absolute` inside
`@media(min-width: 768px)`. Below 768 the wrapper is a plain three-row grid —
`grid-template-areas: "collection-heading" "collection-tab"
"collection-tabcontent"` — with `.list-mainmedia { grid-column: span 2;
height: 300px }` in flow. **The reference's multi-step pinned scroll is a
desktop-only effect.** The port had applied the sticky `100svh` panel at every
breakpoint.

Fix (`ac35f2b`):
- `gsap.matchMedia` branch — `>=768px` keeps the scrub + phase-4 `onUpdate`;
  `<768px` pins nothing, scales nothing, so the hero keeps its 300px
  `--media-height` and the mosaic stacks beneath it.
- stage height moved out of the inline `style={{height:"250svh"}}` into
  `.maya-ft-stage`, so the mobile block can set `height: auto`.
- mobile CSS: panel static/auto, head in flow and never faded, chip deck in
  flow + scrollable, columns stacked, hero static `span 2`, caption pill
  hugging its text.
- dropped a 46px caption override — the reference keeps
  `--text-box-height: 58px` at every size.
- also fixed a stale `[data-ft-image]` selector in `final-check.mjs` (now
  `[data-ft-main]`), which had been silently skipping the hero's animation
  range in that check.

Verified after: mobile `main 360×300`, squares `175×175`, wide `360×216`,
chips `80×60`/`280×60`, caption `260×58` — **element for element the
reference's mobile geometry, zero clipping**. Desktop untouched (`secH 2250`,
hero `matrix(0.7,…,−536,0) → matrix(1,0,0,1,0,0) → matrix(0,0,0,0,0,0)`, tiles
`243×243`/`506×304`). `docH` 20208 desktop / 19479 mobile, both stable over 10

`overflowX false`, scrollWidth 390 = innerWidth 390. `tsc` 0, eslint 0 errors

### Gotcha worth keeping

A sticky panel with `height: 100svh` + `overflow: hidden` is a **clipper**. Any
section ported that way must be checked against the panel box, not the viewport,
at every breakpoint — and the reference may simply not pin at all on small
screens. Always read the theme's media queries for *where* a `position: fixed`
or `position: absolute` is scoped before assuming the desktop behaviour applies
everywhere.
